# 쇼핑 에이전트 — 첫 상세 구조

> 상태: 검토용 설계 초안 · 2026-10-06
> 범위: 쇼핑만. 상품을 고르는 한 번의 판단을 먼저 작동시킨 뒤 메인페이지를 설계한다.

## 1. 만들려는 것

사용자가 사려는 **목적**과 현실 조건을 바탕으로 상품 후보의 확인 가능한 정보를 모아 비교하고, 지금 구매할지·더 확인할지·구매를 미룰지 판단을 돕는다. 최저가 목록이나 대화 기록 앱을 만들려는 것이 아니다. 사용자가 매번 긴 양식을 작성해야 작동하는 방식도 피한다.

첫 결과물은 메인페이지가 아닌 **하나의 쇼핑 판단 상세 화면**이다. 상품 정보·판단 근거·모르는 점·사용자 선택이 한곳에서 확인되어야 한다. 처음에는 사용자가 물건의 이름이나 용도를 한 문장으로 말하거나, 상품 링크·사진을 보내는 흐름으로 검증한다. 장바구니·반복 구매 화면은 상세 판단이 작동한 뒤 검토한다.

## 2. 에이전트가 먼저 모을 자료

사용자에게 자료의 종류나 작업 흐름을 고르게 하지 않는다. **처음에는 구매하려는 물건·용도 또는 상품 링크/사진 중 하나만** 있으면 시작한다. 예: “작은 책상에 둘 조명이 필요해”, 또는 후보 상품 링크 한 개. 처음부터 예산·브랜드·배송지·제약을 모두 채우게 하지 않는다.

| 구분 | 구체적인 자료 | 얻는 방법과 요청 시점 |
|---|---|---|
| 시작에 필요한 단서 | 사려는 물건, 해결하려는 용도, 또는 후보 링크·사진 중 하나 | 사용자에게 짧게 요청. 링크나 사진만 있어도 먼저 읽고 목적이 모호할 때 묻는다. |
| 에이전트가 직접 확인 | 상품 이름·규격, 판매처, 상품가, 배송비, 재고, 반품 조건, 확인 시점 | 허용된 상품 페이지·판매 정보에서 수집. 각 값에 출처를 붙인다. 판매처 접근이 안 되면 값을 만들지 않고 사용자에게 링크 또는 자료를 요청한다. |
| 판단이 막힐 때만 요청 | 예산 상한, 필요한 크기·호환성, 받을 시기, 피하고 싶은 조건 | 어떤 후보가 유리한지 뒤집을 수 있는 항목 **하나만** 이유와 함께 묻는다. |
| 사용자가 원할 때만 활용 | 소유 중인 물건, 과거 구매와 만족도, 자주 쓰는 판매처 | 사용자가 제공·연결을 허용했을 때만 참고한다. 새 요청 하나로 장기 취향을 확정하지 않는다. |

배송비 계산에 지역이 필요하면 먼저 시·군·구 등 최소 범위를 요청한다. 정확한 배송 주소나 결제 정보는 비교 단계에서 요구하지 않는다.

추가 질문은 판단을 바꾸는 정보가 빠졌을 때만 한다. 예를 들어 후보의 배송비가 지역마다 달라 총비용 비교가 불가능하면 “배송비까지 비교하려면 배송 지역이 필요합니다. 시·군·구까지만 알려주실래요?”라고 묻는다. 제품 규격이 호환성을 좌우하면 제품 모델 또는 치수를 묻는다. 답을 받지 못해도 확인 가능한 정보와 모르는 부분은 계속 보여준다.

## 3. 한 번의 판단이 이동하는 경로

```text
구매 목적 또는 상품 후보
  → 상품 정보 수집 (출처·확인 시점 보존)
  → 가격·배송비·반품·크기 등 비교 가능한 사실 정리
  → 예산·필수 조건·피할 조건 적용
  → 후보 간 장단점과 정보가 빈 곳 표시
  → 추천 / 추가 확인 / 구매 보류 중 하나를 이유와 함께 제시
  → 사용자 판단과 구매 여부·이후 만족도를 서로 구분해 반영
```

자료가 모자라면 임의의 가격·재고·성능을 만들지 않는다. 어떤 정보가 빠졌고 왜 구매 판단에 필요한지 말한다. 사용자의 선택은 에이전트의 결론을 덮어쓸 수 있다.

**다음 질문을 고르는 방법:** 후보들을 비교해 순위가 뒤집힐 수 있는 미확인 항목을 찾는다. 호환성처럼 구매 가능 여부를 좌우하는 항목을 먼저, 그다음 총비용·배송 시기·선호 순으로 본다. 그중 사용자만 답할 수 있는 질문 하나를 이유와 함께 요청한다. 판매처에서 확인할 수 있는 정보는 먼저 에이전트가 확인한다. 질문에 답하지 않아도 이미 확인한 비교 결과는 숨기지 않는다.

## 4. 상세 화면 구조 — 메인페이지보다 먼저 제작

1. **상단 한 줄:** 무엇을 사려는지, 가장 중요한 조건, 마지막 정보 확인 시점.
2. **현재 판단:** ‘A가 조건에 가장 맞음’, ‘B의 반품 조건을 먼저 확인’, ‘지금은 구매 보류’처럼 한 가지 결론과 짧은 이유. 결론을 낼 근거가 없으면 추가 확인 요청.
3. **후보 비교:** 각 후보의 총비용(상품가 + 배송비), 필수 조건 충족 여부, 중요한 장점 한 가지와 손해·불확실성 한 가지. 가격만으로 순위를 매기지 않는다.
4. **판단 근거 펼치기:** 원문 링크 또는 업로드 자료, 출처·확인 시각, 관찰된 정보, 추정한 정보, 모르는 정보. 기본 화면에서는 접는다.
5. **사용자 선택:** 저장, 조건 수정, 후보 추가, ‘지금은 사지 않기’. 실제 구매는 사용자가 상점에서 결정한다.
6. **나중에 확인:** ‘유용했음/맞지 않음’과 ‘구매함/구매하지 않음’, 구매 뒤 만족도를 따로 기록한다. 처음부터 응답을 강요하지 않는다.
7. **대화 이어가기:** 현재 판단에 쓰인 사용자 발화와 조건을 함께 보여준다. 발화를 수정·삭제하면 연결된 조건과 판단을 다시 계산한다.

PC·태블릿·휴대폰에서 읽는 순서는 같다. 넓은 화면은 비교 후보를 나란히 놓고, 좁은 화면은 후보 카드를 세로로 놓는다. 하단까지 긴 입력 양식을 늘어놓지 않는다.

## 5. 내부 데이터 구조

| 객체 | 최소 정보 | 목적 |
|---|---|---|
| `ShoppingPurpose` | 목적, 생성 시점, 상태 | 무엇을 해결하려는 구매인지 보존 |
| `Criterion` | 예산·필수·선호·피할 조건, 사용자 확인 여부 | 비교 기준을 명시하고 수정 가능하게 함 |
| `Candidate` | 제품 식별자, 링크/제공 자료, 제품 속성 | 비교 대상 |
| `Offer` | 판매처, 가격, 배송비, 재고, 반품 조건, 확인 시점 | 시점에 따라 바뀌는 판매 조건 |
| `Evidence` | 출처, 수집 시점, 원문 또는 사용자가 제공한 자료, 추출값 | 사실의 근거와 정정 경로 |
| `Evaluation` | 통과/제외 조건, 장단점, 미확인 항목, 제안 이유 | 비교 결과를 재현 가능하게 함 |
| `Feedback` | 관련성 평가, 고려 의사, 실제 구매, 이후 만족도 | 다른 의미의 반응을 섞지 않음 |
| `ConversationTurn` | 화자, 원문, 시각, 연결된 쇼핑 건, 수정·삭제 상태 | 대화의 맥락과 정정 이력 보존 |
| `ConversationFact` | 내용, 종류, 확정/미확인, 출처 발화 ID, 적용 범위, 갱신 시각 | 다음 판단에서 쓸 수 있는 확인된 정보 |

사용자에게 내부 객체 이름을 화면 메뉴로 보여주지 않는다. 가격·재고·배송·반품처럼 자주 변하는 정보는 상품의 고정 속성과 분리한다. 확인되지 않은 값은 `unknown`으로 남긴다. 새 상품 링크를 받아도 사용자가 원치 않는 장기 선호로 자동 확정하지 않는다.

대화 원문과 판단에 쓰는 정보를 분리한다. 조건은 반드시 근거가 되는 사용자 발화에 연결하고 기본 적용 범위를 **해당 쇼핑 건**으로 둔다. 에이전트의 추측은 사용자 확인 전까지 확정 조건에 넣지 않는다. 수정·삭제 시 원문 접근 권한을 확인하고 연결된 조건을 갱신하거나 무효화한 뒤 판단을 다시 계산한다. 삭제된 발화의 본문은 사용자 화면과 이후 판단에서 제거한다. 운영 환경의 보존·완전 삭제 정책은 별도 결정이 필요하다.

다음 대화에서는 현재 쇼핑 건의 유효한 조건을 먼저 읽고, 다른 구매 건의 정보는 사용자가 재사용을 허용한 경우에만 참고한다. 이전 반응은 ‘선호한다’라는 단정 대신 해당 제안에 대한 반응으로 읽는다. 테스트 시제품은 자유 문장에서 의미를 자동 추출하지 않는다. 사용자가 선택지로 명시한 우선 조건만 확정 조건으로 저장하고, 자유 입력은 원문으로 보존한다.

## 6. 첫 판단 규칙

1. 필수 조건을 충족하지 않는 후보는 이유를 보이며 제외한다. 정보가 없는 후보는 ‘불합격’이 아니라 ‘확인 필요’로 표시한다.
2. 비교 가능한 총비용을 계산하되, 배송비나 옵션 가격이 없으면 합계를 확정하지 않는다.
3. 가격·재고·반품 조건에는 확인 시각을 붙이고 오래된 정보는 재확인 대상으로 만든다.
4. 후보가 모두 부적합하거나 구매 목적이 불분명하면 구매를 권하지 않는다.
5. 한 번에 하나의 다음 판단만 제시한다. 예: ‘B의 반품 조건 확인’, ‘A 선택’, ‘구매 보류’.
6. 사용자의 수정·반론을 반영해 비교를 다시 계산한다. 반응 하나로 영구적인 취향을 단정하지 않는다.

## 7. 첫 검증 사례: 작은 기기의 화면 보호

첫 구매 목적은 **새로 산 손목 기기의 화면을 보호하는 것**이다. 사용자가 두 상품 링크와 판매 화면을 주었고, 추가 질문에 **측면·모서리까지 덮는 케이스형 보호**를 우선한다고 답했다. 이 경우 에이전트는 같은 검색 결과에 있는 상품이라도 서로 다른 보호 방식임을 먼저 밝혀야 한다.

| 항목 | 합성 후보 A: 화면과 테두리를 덮는 케이스 | 합성 후보 B: 화면에 붙이는 필름 |
|---|---|---|
| 확인할 제품 속성 | 기기 모델 호환, 화면부와 측면의 실제 덮임 범위, 터치와 버튼 사용 | 기기 모델 호환, 화면 덮임 범위, 부착·교체 방식 |
| 사용자의 조건과 관계 | 측면·모서리 보호 목적에 우선 부합할 가능성 | 화면 표면 보호 목적에는 맞지만 측면 보호는 별도 확인 필요 |
| 화면의 판단 | 조건부 우선 후보. 덮임 범위와 조작성을 확인한 뒤 구매 판단 | 사용자가 얇은 착용감을 우선하면 다시 비교 |

**상세 화면의 첫 화면 예시**

```text
갤럭시 핏3 화면과 모서리 보호
우선 조건: 측면·모서리까지 덮는 케이스

현재 판단  케이스형 후보를 먼저 확인하세요.
이유        필름형 후보는 화면 부착 방식이어서 요청한 측면 보호를
            충족하는지 확인되지 않았습니다.
확인할 점   케이스가 화면과 측면을 실제로 어디까지 덮는지,
            터치·버튼 조작에 불편은 없는지 판매 상세 정보 확인

[케이스형 후보]  목적 적합성: 높을 가능성 · 실제 덮임 범위: 확인 필요
[필름형 후보]  화면 보호: 가능성 있음 · 측면 보호: 확인되지 않음

[근거와 가격 확인 시점 보기] [조건 바꾸기] [판매처에서 보기]
```

두 상품의 가격을 단순히 `1개 가격` 대 `3장 가격`으로 비교하지 않는다. 보호 대상과 교체 단위가 다르기 때문이다. 리뷰 수와 판매 배지도 성능의 증거로 삼지 않는다. 배송 예정일·할인가·옵션별 가격은 시점과 계정·지역에 따라 달라질 수 있으므로, 사용자 스크린샷의 값은 **캡처 당시의 관찰**로만 남긴다. 판매 페이지가 차단되면 최신 값이나 반품 조건을 확인했다고 표시하지 않는다.

이 사례의 초기 질문은 “원하는 보호 범위” 하나였다. 답을 받은 뒤에는 같은 질문을 반복하지 않고, 판매 정보에서 확인할 수 있는 실제 덮임 범위와 조작성을 에이전트가 먼저 확인한다. 사용자가 제공하지 않은 건강·구매 이력·주소를 요구하지 않는다.

## 8. 합성 검증 자료와 완료 기준

실제 상품·계정·영수증은 공개 저장소에 넣지 않는다. 합성 상품 2~3개와 합성 판매 조건으로 다음을 확인한다.

- 사용자가 예산 또는 피할 조건 하나만 알려줘도 비교가 시작된다.
- 물건·용도 한 문장이나 상품 링크 하나로 시작하고, 나머지 상품 정보는 에이전트가 가능한 범위에서 모은다.
- 추가 정보가 필요할 때는 판단에 영향을 주는 질문 하나와 그 이유만 제시한다.
- 상품가가 낮아도 배송비를 합하면 더 비쌀 수 있음을 정확히 보여준다.
- 반품 조건이 비어 있으면 확신에 찬 추천 대신 확인 요청을 한다.
- 예산이나 필수 조건을 바꾸면 판단과 제외 이유가 함께 바뀐다.
- ‘좋아 보임’이 구매 완료나 만족으로 기록되지 않는다.
- 사용자의 조건 발화가 출처로 표시되고, 수정·삭제 후 조건과 비교 판단이 함께 바뀐다.
- 재접속해도 대화 원문과 조건·반응이 복구된다.
- 좁은 화면에서도 현재 판단과 두 후보의 핵심 차이를 긴 스크롤 없이 찾을 수 있다.

이 검사 후에야 상세 화면에서 반복되는 정보를 바탕으로 메인페이지의 정보 구조를 정한다. 메인페이지를 먼저 꾸며 기능의 목적을 역으로 맞추지 않는다.

## 9. 아직 결정되지 않은 것

- 첫 분야는 작은 기기의 보호 액세서리로 정했다. 판매처·가격 정보의 안정적인 출처는 아직 없다. 합성 검증이 끝나기 전에는 실시간 가격을 제공한다고 약속하지 않는다.
- 자동 수집 주기와 상품 링크·영수증·스크린샷을 처리할 범위.
- 여러 기기 간 동기화와 계정 설정을 실사용 단계에서 어떻게 제공할지. 로그인 없는 합성 체험과 실사용 데이터 저장은 분리한다.

이전 탐색 시제품의 ‘새 이야기/이전 이야기’ 화면은 이 쇼핑 상세 구조의 화면 명세가 아니다.
