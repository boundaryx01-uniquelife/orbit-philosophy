## 선택 또는 판단

웹북에서 바로 교정할 때 수정 내용을 GitHub 원고에 곧바로 반영할지, 브라우저에 임시 저장한 뒤 검토할지 결정한다.

## 선택지와 근거

| 선택지 | 기대 효과 | 비용·위험 | 근거 종류 | 근거 |
|---|---|---|---|---|
| 1. 공개 웹에서 GitHub 원고를 직접 수정 | 읽기와 반영이 한 번에 끝남 | 로그인·쓰기 권한·충돌 처리·실수 복구가 필요하며 원문이 즉시 바뀜 | `CONSTRAINT` | 정적 GitHub Pages만으로 안전하게 구현할 수 없음 |
| 2. 브라우저 자동 저장 후 Markdown 내보내기 | 읽으며 즉시 고치되 원문 반영 전 검토 가능 | 다른 기기에는 자동 동기화되지 않고 파일을 한 번 전달해야 함 | `CONSTRAINT`, `INFERENCE` | 원문과 교정본의 경계를 유지하면서 정적 웹에서 구현 가능 |
| 3. 문장별 메모만 남기기 | 원문 훼손 위험이 가장 낮음 | 실제 문장으로 고친 결과를 다시 작성해야 함 | `INFERENCE` | 초기 의견 수집에는 적합하지만 직접 교정 요구와 거리가 있음 |

## 현재 선택

- 임시 선택: **2. 브라우저에 자동 저장하고 Markdown 교정본으로 내보낸다.**
- 적용 범위: 웹북 v0.1의 본문 전체
- 보호 경계: 공개 페이지는 저장소 파일을 직접 변경하거나 GitHub 쓰기 권한을 요구하지 않는다.
- 최종 판단: 사용자가 실제 교정 흐름을 사용한 뒤 유지·수정·폐기를 결정한다.

## 구현된 흐름

1. `교정 시작`을 눌러 본문을 직접 수정한다.
2. 수정 내용은 현재 브라우저의 `localStorage`에 자동 저장된다.
3. 새로고침 후 저장된 교정본을 다시 불러온다.
4. 전체 수정본을 Markdown으로 내려받는다.
5. 내려받은 파일을 검토한 뒤 원고 반영 여부를 별도로 판단한다.
6. `원문으로 복원`은 확인 뒤 브라우저의 임시 교정본만 제거한다.

## 검증할 질문

- 읽기 흐름을 끊지 않고 교정 모드로 전환할 수 있는가?
- 자동 저장 상태를 사용자가 분명히 이해하는가?
- Markdown 결과가 원고 병합에 충분한 구조를 유지하는가?
- 직접 GitHub 반영이 없다는 경계가 번거로움보다 안전에 기여하는가?
